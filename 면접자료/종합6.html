🚀 Part 1. 인프라 및 배포 (미경험 방어)

Q.EC2에 직접 배포하셨는데, 혹시 GitHub Actions나 Jenkins 같은 CI/CD 도구를 사용해 배포 자동화를 구축해 보셨나요?

🎯 면접관의 의도

DevOps 역량을 묻습니다. 경험이 없다면 거짓말을 하기보다는 수동 배포의 '불편함'을 어떻게 인지하고 있으며, 이를 자동화로 해결하려는 '학습 의지'가 있는지를 보여주어야 합니다.

✅ 모범 답변 가이드

(솔직한 인정 + 불편함 체감 어필 + 학습 의지)
"솔직히 말씀드리면 이번 프로젝트에서는 기한이 빠듯하여 CI/CD 파이프라인까지는 구축하지 못했습니다. 로컬에서 직접 Maven으로 JAR 파일을 빌드하고, FileZilla로 EC2에 넘긴 뒤 nohup으로 서버를 띄우는 수동 배포 방식을 사용했습니다."

"하지만 이 수동 배포 과정을 하루에도 몇 번씩 반복하다 보니, 휴먼 에러가 발생하기 쉽고 개발 흐름이 끊긴다는 것을 뼈저리게 느꼈습니다. 비록 이번엔 적용하지 못했지만, 자동화의 필요성을 누구보다 절감했기 때문에 입사 전후로 반드시 GitHub Actions를 활용한 빌드/테스트/배포 자동화 파이프라인을 학습하여 실무 환경에 빠르게 적응하겠습니다."

🐛 Part 2. 로깅(Logging) 및 트러블슈팅

Q.서버 운영 중 문제가 발생했을 때 어떻게 원인을 찾나요? Logback이나 Log4j 같은 전문 로깅 프레임워크를 적용해 보셨나요?

🎯 면접관의 의도

문제가 터졌을 때 콘솔에만 의존하는지, 파일 단위로 로그를 남겨 추적할 수 있는지를 봅니다. 이 역시 경험이 없다면 한계를 인지하고 있음을 논리적으로 방어해야 합니다.

✅ 모범 답변 가이드

"프로젝트 초기에는 System.out.println()이나 기본 콘솔 로그에 의존하여 디버깅을 진행했습니다. EC2 서버 운영 중에는 nohup.out 파일에 남겨진 에러 스택 트레이스를 보며 원인을 파악했습니다."

"하지만 System.out.println()은 동기적으로 동작하여 서버 성능을 저하시키고, 방대한 로그를 파일별로 관리하거나 레벨(INFO, DEBUG, ERROR)을 나누어 필터링할 수 없다는 치명적인 한계를 깨달았습니다. 전문 로깅 프레임워크를 직접 설정해 보진 못했으나, 실무에서는 장애 추적과 운영 모니터링을 위해 SLF4J와 Logback을 사용한 체계적인 로그 관리가 필수적이라는 점을 잘 인지하고 있습니다."

🌿 Part 3. 버전 관리 및 Git 협업 전략

Q.팀 프로젝트 시 Git 브랜치(Branch) 전략은 어떻게 가져갔나요? 두 명이 같은 파일을 수정해서 심각한 Merge Conflict(충돌)가 났을 때 어떻게 해결했나요?

🎯 면접관의 의도

실제 협업 과정에서 충돌을 회피하기 위한 컨벤션을 지켰는지, 그리고 충돌이 났을 때 강제 푸시(Force Push) 같은 독단적인 행동을 하지 않고 소통으로 풀었는지 봅니다.

✅ 모범 답변 가이드

"단순화된 Git Flow 전략을 사용했습니다. 배포용 main 브랜치와 개발용 dev 브랜치를 두고, 각자 기능을 개발할 때는 feature/login 처럼 브랜치를 분기하여 작업 후 Pull Request(PR)를 날리는 방식을 따랐습니다."

"충돌(Conflict)이 발생했을 때 저는 절대 임의로 코드를 덮어쓰거나 강제 푸시를 하지 않았습니다. 반드시 충돌이 발생한 코드를 작성한 팀원과 직접 만나거나 화상 화면을 켜놓고, 각자의 비즈니스 로직을 리뷰하며 어느 코드를 남겨야 할지 합의한 뒤에 수동으로 병합(Merge)을 완료했습니다. 소통이 가장 확실한 충돌 해결법이었습니다."

🤝 Part 4. AI 보조 개발론 및 코드 리뷰

Q.팀원들이 각자 AI를 써서 코드를 짜오면 코드 스타일이나 아키텍처가 중구난방이 될 텐데, 이를 맞추기 위한 팀 내 가이드라인이나 컨벤션이 있었나요?

🎯 면접관의 의도

단순히 개인적으로 AI를 쓰는 것을 넘어, 팀 단위의 코드 유지보수성과 품질을 통제할 수 있는 주도적인 협업 역량을 높게 평가하기 위한 질문입니다.

✅ 모범 답변 가이드

"정확히 그 문제를 프로젝트 초기에 겪었습니다. 이를 방지하기 위해 팀원들과 함께 AI 협업 가이드라인을 마크다운(Markdown) 문서로 명확히 작성하여 공유했습니다."

"가이드라인에는 'AI가 생성한 코드는 무비판적으로 복사하지 말 것', '변수명과 메서드명은 팀의 카멜 케이스(Camel Case) 네이밍 룰을 따르게 프롬프트를 조정할 것' 등의 규칙을 담았습니다. 또한, GitHub PR(Pull Request) 시 코드 리뷰 단계에서 AI가 작성한 코드라도 팀의 아키텍처 규칙에 맞게 리팩토링되었는지 상호 꼼꼼하게 검증하는 과정을 거쳐 코드의 일관성을 유지할 수 있었습니다."
