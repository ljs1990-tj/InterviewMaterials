🌱 Spring 면접 시크릿 노트: Core & MVC

개발자가 아닌 '스프링 컨테이너'가 애플리케이션을 지배하는 IoC/DI 사상과 Boot의 자동화 원리를 증명하세요.

Q.(필수 기출) 기존의 Spring Framework와 Spring Boot의 결정적인 차이점은 무엇인가요? 왜 Boot를 사용하셨나요?

🎯 면접관의 의도

단순히 남들이 쓰니까 쓰는 것이 아니라, 과거 레거시 스프링의 고질적인 문제(환경설정 지옥)를 이해하고 Boot가 이를 어떻게 기술적으로 해결했는지 파악하고 있는지 묻습니다.

✅ 모범 답변 가이드

가장 큰 차이는 '설정의 자동화'와 '내장 웹 서버'의 유무입니다.
  • 1. 자동 설정 (Auto-Configuration): 기존 Spring은 프로젝트 세팅을 위해 엄청난 양의 XML 파일 설정과 라이브러리 버전 호환성을 개발자가 직접 맞춰야 했습니다. 반면 Spring Boot는 @SpringBootApplication 어노테이션을 통해 자주 쓰는 설정들을 관례에 따라 자동으로 설정(Auto Configuration)해 주고, starter 의존성을 통해 버전 충돌을 알아서 해결해 줍니다.
  • 2. 내장 WAS (Embedded Server): 기존에는 Tomcat 같은 웹 서버(WAS)를 따로 설치하고 WAR 파일로 빌드해서 배포해야 했습니다. 하지만 Boot는 Tomcat이 내장되어 있어 독립적으로 실행 가능한 JAR 파일 하나만 빌드하면 바로 서버를 띄울 수 있어 배포가 압도적으로 편리해졌습니다.
#SpringBoot #AutoConfiguration #내장Tomcat

Q.스프링의 핵심 사상인 IoC(제어의 역전)와 DI(의존성 주입)에 대해 본인의 언어로 설명해 주시겠어요?

🎯 면접관의 의도

스프링 컨테이너의 존재 이유를 묻는 가장 근본적인 질문입니다. 객체의 생명주기를 누가 관리하며, 왜 결합도를 낮춰야 하는지 객체지향적 관점에서 설명해야 합니다.

✅ 모범 답변 가이드

1. IoC (Inversion of Control, 제어의 역전):
기존에는 개발자가 직접 new 키워드로 객체를 생성하고 관리했습니다. 하지만 스프링에서는 객체의 생성부터 소멸까지의 주도권(제어권)을 개발자가 아닌 '스프링 컨테이너'가 가져갑니다. 이를 제어의 역전이라고 합니다.

2. DI (Dependency Injection, 의존성 주입):
IoC를 구현하는 구체적인 방법입니다. 객체 내부에서 사용할 다른 객체를 직접 생성하지 않고, 외부(스프링 컨테이너)에서 만들어진 객체(Bean)를 조립하듯 주입받는 것입니다.
덕분에 부품을 갈아 끼우기 쉬워져 객체 간의 결합도가 낮아지고(느슨한 결합), 테스트 코드를 작성하거나 유지보수하기가 훨씬 수월해집니다.
#IoC #DI #느슨한결합

Q.DI(의존성 주입) 방식에는 필드 주입, 수정자(Setter) 주입, 생성자 주입이 있는데, 왜 가급적 '생성자 주입'을 권장하나요?

🎯 면접관의 의도

실무에서 @Autowired를 필드에 무분별하게 남발하지 않는지, 불변성(Immutability)과 순환 참조의 개념을 인지하고 코드를 짜는지 확인하는 실무 밀착형 질문입니다.

✅ 모범 답변 가이드

스프링 공식 문서에서도 생성자 주입(Constructor Injection)을 강력히 권장하며, 그 이유는 크게 3가지입니다.
  • 1. 불변성 보장: 객체 생성 시점에 의존성이 딱 한 번만 주입되므로, 필드에 final 키워드를 선언할 수 있습니다. 런타임에 의존성이 임의로 변경되는 버그를 원천 차단합니다.
  • 2. 순환 참조 사전 방지: A가 B를 참조하고 B가 A를 참조하는 순환 참조 상태일 때, 필드 주입은 앱이 실행되다가 해당 메서드를 호출할 때야 에러가 터집니다. 하지만 생성자 주입은 애플리케이션 구동(컴파일) 시점에 즉시 에러를 뱉어내어 치명적인 장애를 미리 막아줍니다.
  • 3. POJO 테스트 용이: 스프링 컨테이너 없이도 순수 자바 코드로 단위 테스트(Unit Test)를 작성할 때 직접 목(Mock) 객체를 주입하기 가장 좋습니다.
#생성자주입 #불변성 #순환참조방지

Q.스프링 빈(Bean)은 기본적으로 싱글톤(Singleton)으로 관리됩니다. 왜 싱글톤을 쓰며, 개발 시 어떤 점을 가장 주의해야 하나요?

🎯 면접관의 의도

트래픽이 몰리는 웹 서버의 특성을 이해하고 있는지, 멀티스레드 환경에서 싱글톤 객체가 가질 수 있는 '상태 유지(Stateful)'의 위험성을 알고 있는지 검증합니다.

✅ 모범 답변 가이드

1. 싱글톤을 쓰는 이유:
대규모 트래픽이 발생하는 웹 환경에서, 요청이 올 때마다 Controller나 Service 객체를 new로 새로 생성하면 메모리 낭비가 극심합니다. 따라서 스프링 컨테이너 구동 시 객체를 딱 1개만 생성해두고 모든 사용자의 요청이 그 객체를 공유(재사용)하여 메모리 효율을 극대화합니다.

2. 주의할 점 (무상태성 유지):
여러 스레드(사용자)가 하나의 빈 객체를 동시에 공유하므로, 절대 객체 내부에 특정 클라이언트에 의존적인 상태(공유 필드 변수)를 유지하게 설계하면 안 됩니다(Stateless 설계). 만약 사용자 정보를 전역 변수 필드에 저장하면, A 사용자의 데이터가 B 사용자에게 노출되는 끔찍한 동시성 사고가 발생할 수 있습니다.
#SpringBean #Singleton #Stateless

Q.스프링의 AOP(Aspect-Oriented Programming)란 무엇이고, 실무에서 어떤 기능들을 구현할 때 주로 사용하나요?

🎯 면접관의 의도

비즈니스 로직과 공통 부가 로직을 분리하여 코드의 중복을 줄이고 유지보수성을 높이는 횡단 관심사(Cross-Cutting Concerns)의 개념을 묻는 질문입니다.

✅ 모범 답변 가이드

1. AOP의 개념:
애플리케이션 전반에 걸쳐 공통적으로 반복되는 기능(부가 기능)들을 핵심 비즈니스 로직에서 떼어내어 별도의 모듈(Aspect)로 분리하고, 필요한 시점(Pointcut)에 동적으로 끼워 넣는 기법입니다.

2. 실무 활용 사례 (횡단 관심사):
Service 클래스의 수많은 메서드들에 매번 로그를 찍는 코드를 넣으면 중복이 발생합니다. 이때 AOP를 활용해 1) API 실행 시간 측정 로그, 2) DB 트랜잭션 관리(@Transactional), 3) 권한/인가 체크 등을 비즈니스 로직 코드 수정 없이 외부에서 투명하게 적용할 수 있습니다.
#AOP #횡단관심사 #트랜잭션관리
