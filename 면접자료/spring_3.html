🛡️ Spring 면접 시크릿 노트: Security & REST API

인증/인가 원리와 RESTful API 통신 규약을 이해하고, 배포 경험을 논리적으로 어필하세요.

Q.(기출) 프로젝트에서 Spring Security와 JWT를 활용해 사용자 보안 관리를 하셨는데, 구체적인 동작 방식과 JWT를 선택한 이유를 설명해 주세요.

🎯 면접관의 의도

단순히 남의 코드를 복붙한 것인지, 아니면 세션(Session) 기반 인증의 한계를 인지하고 토큰(Token) 기반 인증의 Stateless(무상태성) 이점을 확실히 알고 설계했는지 검증합니다.

✅ 모범 답변 가이드

1. JWT를 선택한 이유:
기존 세션 방식은 사용자가 늘어날수록 서버 메모리 부하가 심해지고 서버 확장에 불리합니다. 반면 JWT는 사용자 정보를 해시된 토큰 자체에 담아 클라이언트가 보관하므로, 서버를 무상태(Stateless)로 가볍게 유지할 수 있어 선택했습니다.

2. Spring Security와의 결합 동작:
Spring Security의 필터 체인(Filter Chain) 중간에 커스텀 필터(JwtAuthenticationFilter)를 끼워 넣었습니다. 클라이언트가 API를 요청할 때 HTTP 헤더에 담아 보낸 JWT를 가로채서 서명(Signature)이 유효한지 검증하고, 정상이라면 SecurityContextHolder에 권한 정보를 저장하여 Controller에서 인증된 사용자로 처리되도록 구현했습니다.
#SpringSecurity #JWT #Stateless

Q.(기출) 브라우저 요청 방식에 GET과 POST 외에 어떤 것들이 있나요? 그리고 RESTful API란 무엇이라고 생각하나요?

🎯 면접관의 의도

프론트엔드와 백엔드가 협업하기 위한 API 설계 규약을 아는지 묻습니다. CRUD 작업에 맞는 HTTP 메서드 매핑 능력을 확인합니다.

✅ 모범 답변 가이드

1. HTTP 메서드의 종류 (CRUD 매핑):
GET(조회), POST(생성) 외에도 데이터의 전체 수정을 뜻하는 PUT, 부분 수정인 PATCH, 데이터 삭제를 뜻하는 DELETE가 있습니다.

2. RESTful API의 핵심:
URL 주소에 'insert', 'update' 같은 행위(동사)를 적지 않고 오직 조작할 대상(명사 자원)만 명시하는 아키텍처 스타일입니다.
예를 들어 유저 정보를 수정할 때 /updateUser/1 (POST) 처럼 짜는 것이 아니라, /users/1 (PATCH) 형태로 자원(URI)과 행위(Method)를 분리하여 누구나 직관적으로 API의 목적을 알 수 있게 설계하는 것입니다.
#RESTful_API #HTTPMethod #PUT_PATCH_DELETE

Q.(기출) 사용자 로그인을 구현할 때 주로 묻는 세션(Session)과 쿠키(Cookie)의 차이점은 무엇인가요?

🎯 면접관의 의도

HTTP의 본질적인 무상태성(Stateless)을 극복하기 위한 상태 유지 기술을 정확히 비교하고, 보안 관점에서의 장단점을 파악하고 있는지 확인합니다.

✅ 모범 답변 가이드

두 기술의 가장 큰 차이는 '데이터의 저장 위치'와 '보안성'입니다.
  • 쿠키 (Cookie): 사용자 정보가 클라이언트(브라우저)에 텍스트 형태로 저장됩니다. 서버 부하가 없지만, 누구나 열어볼 수 있어 탈취 및 위변조 위험(보안 취약)이 매우 큽니다.
  • 세션 (Session): 중요 정보는 서버의 메모리에 안전하게 저장하고, 클라이언트에게는 난수로 생성된 JSESSIONID(출입증)만 쿠키를 통해 발급합니다. 보안은 뛰어나지만, 접속자가 많아지면 서버 메모리가 버티지 못하는 단점이 있습니다. (이를 보완하기 위해 나온 것이 바로 JWT입니다.)
#세션 #쿠키 #인증방식

Q.(기출) MVC 패턴의 Model 1과 Model 2의 차이는 무엇이고, 현재 사용 중인 Spring MVC는 어느 쪽에 해당하나요?

🎯 면접관의 의도

웹 개발 아키텍처의 과거와 현재를 묻는 기초 질문입니다. 비즈니스 로직(Controller)과 화면(View)의 분리가 왜 중요한지 알고 있는지 평가합니다.

✅ 모범 답변 가이드

  • Model 1: JSP 파일 하나 안에 화면 그리는 HTML 코드와 데이터베이스를 조회하는 자바 코드가 전부 섞여 있는 방식입니다. 개발은 빠르지만 코드가 복잡해져 유지보수가 끔찍합니다.
  • Model 2: 클라이언트의 요청을 서블릿(Controller)이 먼저 받아 비즈니스 로직을 처리한 후, 결과(Model)만 화면(JSP/Thymeleaf)으로 넘겨 화면을 그리는 방식입니다. 디자이너와 개발자의 작업 영역이 분리됩니다.
현재 사용하는 Spring MVC는 철저한 Model 2 방식을 발전시킨 프레임워크이며, 모든 요청을 먼저 받아 분배하는 DispatcherServlet(Front Controller 패턴)을 핵심으로 사용하고 있습니다.
#MVC패턴 #Model2 #DispatcherServlet

Q.(기출) 로컬 환경에서 테스트하는 것을 넘어, 굳이 AWS를 이용해서 프로젝트를 클라우드에 배포한 이유가 있나요?

🎯 면접관의 의도

단순히 학원 튜토리얼을 따라 한 것인지, 아니면 온프레미스(물리 서버 직접 구축) 대비 클라우드 서버의 이점을 스스로 이해하고 도입했는지 확인합니다.

✅ 모범 답변 가이드

크게 비용적 이점과 유연성 때문에 AWS(EC2/RDS 등)를 선택했습니다.

개인 프로젝트를 위해 물리적인 24시간 가동 서버 하드웨어를 구매하고 네트워크를 설정하는 것은 비효율적입니다. AWS를 이용하면 초기 인프라 구축 비용 없이 가상의 컴퓨터(EC2)를 빌려 쓴 만큼만 지불하면 되고, 물리적인 하드웨어 관리에 신경 쓰지 않고 애플리케이션 개발에만 온전히 집중할 수 있기 때문입니다.

추가로, 실무에서 트래픽이 몰렸을 때 서버 사양을 버튼 몇 개로 유연하게 늘리거나 줄일 수 있는 클라우드의 강력한 탄력성(Elastic)을 직접 경험해 보고 싶었습니다.
#AWS배포 #CloudInfra #EC2_RDS
