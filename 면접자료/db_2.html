Q.(기출) DB에서 프로시저(Procedure)와 트리거(Trigger)를 써본 적 있나요? 이 둘의 차이점과 실무에서의 장단점을 설명해 주세요.

🎯 면접관의 의도

DB 내부 프로그래밍(PL/SQL 등) 경험을 묻는 질문입니다. 장점뿐만 아니라, 최근 트렌드에서 이를 지양하는 이유(단점)까지 객관적으로 파악하고 있는지 묻습니다.

✅ 모범 답변 가이드

1. 두 개념의 차이:
  • 프로시저: 여러 개의 SQL 문을 마치 하나의 함수처럼 DB에 저장해 두고, 애플리케이션에서 CALL 명령어로 호출해서 사용하는 수동 실행 방식입니다.
  • 트리거: 특정 테이블에 INSERT, UPDATE, DELETE 이벤트가 발생하면, 개발자가 호출하지 않아도 자동(방아쇠)으로 실행되는 로직입니다. 주로 데이터 삽입/삭제 시 백업 로그를 남길 때 씁니다.
2. 장단점 (핵심 어필):
복잡한 연산을 DB에서 바로 처리하므로 네트워크 트래픽이 줄어 속도가 매우 빠르다는 장점이 있습니다. 하지만 로직이 DB에 묶여버리기 때문에 Git으로 버전 관리를 하기가 어렵고, 에러 발생 시 디버깅이 힘들어 최신 백엔드 트렌드에서는 비즈니스 로직을 가급적 자바(서버) 쪽으로 빼는 추세입니다.
#Procedure #Trigger #DB프로그래밍

Q.데이터베이스 설계 시 '정규화(Normalization)'를 하는 이유는 무엇인가요? 그렇다면 '반정규화(De-normalization)'는 왜 하는 걸까요?

🎯 면접관의 의도

테이블 설계(ERD) 능력을 평가합니다. 무조건적인 원칙 준수(정규화)보다, 서비스 성능을 위해 원칙을 깨는 유연함(반정규화)을 아는지 확인합니다.

✅ 모범 답변 가이드

1. 정규화를 하는 이유:
하나의 테이블에 너무 많은 정보를 때려 넣으면 데이터가 불필요하게 중복됩니다. 이로 인해 데이터를 수정하거나 삭제할 때 꼬여버리는 이상 현상(Anomaly)이 발생하므로, 테이블을 잘게 쪼개어 데이터의 무결성과 일관성을 지키기 위해 정규화를 합니다.

2. 반정규화를 하는 이유 (Trade-off):
하지만 테이블을 너무 많이 쪼개놓으면, 게시판 글 하나를 읽을 때마다 테이블 5~6개를 조인(Join)해야 해서 조회(SELECT) 성능이 극도로 저하됩니다. 따라서 데이터의 무결성을 조금 포기하더라도, 응답 속도를 높이기 위해 의도적으로 데이터를 중복 저장하거나 테이블을 다시 합치는 것을 반정규화라고 합니다.
#정규화 #반정규화 #이상현상(Anomaly)

Q.DB에서 뷰(View) 객체는 무엇이며, 굳이 실제 테이블이 아닌 가상 테이블(View)을 만들어 사용하는 이유는 무엇인가요?

🎯 면접관의 의도

복잡한 쿼리를 추상화하여 사용자의 편의성을 높이고, 중요한 데이터를 은닉하는 DB 보안 관점의 지식을 묻습니다.

✅ 모범 답변 가이드

뷰(View)는 물리적인 데이터를 가지지 않고, 자주 사용하는 SELECT 쿼리문 자체를 저장해 둔 '가상 테이블'입니다.

사용하는 주된 이유는 두 가지입니다.
  • 편의성: 복잡한 JOIN이 떡칠된 쿼리를 뷰로 만들어 두면, 개발자는 단순히 SELECT * FROM view_name만 쳐도 되므로 코드가 훨씬 깔끔해집니다.
  • 보안(은닉화): 사원 테이블에 '연봉'이나 '주민번호' 같은 민감한 정보가 있을 때, 이 컬럼들을 제외한 나머지 정보만 묶어서 뷰로 제공함으로써 외부 개발자나 사용자가 민감한 데이터에 접근하는 것을 원천 차단할 수 있습니다.
#View #DB보안 #가상테이블

Q.게시판에 데이터가 1,000만 건이 있습니다. 기존의 LIMIT, OFFSET 방식으로 마지막 페이지를 조회하면 매우 느린데, 이를 어떻게 최적화할 수 있을까요?

🎯 면접관의 의도

실제 서비스에서 트래픽이 커졌을 때 발생하는 가장 대표적인 성능 이슈(병목)인 '페이징 성능 저하'를 해결할 수 있는 능력이 있는지 묻는 고급 튜닝 질문입니다.

✅ 모범 답변 가이드

1. 기존 방식의 문제점 (LIMIT, OFFSET):
LIMIT 9999000, 10 처럼 쿼리를 날리면, DB는 999만 9천 번 째까지 데이터를 다 읽은 다음 앞의 것들을 버리고 마지막 10개만 가져옵니다. 뒤로 갈수록 읽어야 할 데이터가 기하급수적으로 늘어나 풀 스캔에 가까운 부하가 발생합니다.

2. 해결책 (No-Offset / 커서 기반 페이징):
마지막으로 조회했던 게시글의 PK(예: id = 9999000)를 클라이언트가 기억했다가 서버로 넘겨줍니다.
그리고 쿼리를 WHERE id > 9999000 LIMIT 10 처럼 작성하면, PK 인덱스를 타고 해당 위치로 즉시 점프(Index Seek)한 뒤 딱 10개만 읽고 끝나므로 데이터가 아무리 많아도 조회 속도가 0.1초 이내로 일정하게 유지됩니다.
#페이징최적화 #No-Offset #Cursor페이징

Q.수강신청이나 티켓팅처럼 여러 사용자가 동시에 동일한 데이터(재고)를 수정하려고 할 때 발생하는 문제를 어떻게 해결할 수 있나요?

🎯 면접관의 의도

동시성 제어(Concurrency Control)에 대한 이해도를 평가합니다. DB Lock의 개념을 알고 데이터 정합성을 지킬 수 있는지 확인하는 고급 질문입니다.

✅ 모범 답변 가이드

여러 트랜잭션이 동시에 같은 데이터를 수정하려 하면 갱신 손실(Lost Update) 등 데이터 정합성이 깨지는 문제가 발생합니다. 이를 막기 위해 DB Lock(락)을 사용해야 합니다.

  • 비관적 락(Pessimistic Lock): "무조건 충돌이 날 것이다"라고 가정하고, SELECT ... FOR UPDATE 쿼리를 통해 데이터를 읽는 시점부터 아예 DB 행(Row)에 배타 락(X-Lock)을 걸어버리는 방법입니다. 한 사람이 수정을 마칠 때까지 다른 사람은 대기하게 되므로 데이터 안전성이 매우 높지만, 속도가 느려질 수 있습니다.
  • 낙관적 락(Optimistic Lock): 테이블에 version 컬럼을 추가하여, 내가 읽었던 버전과 수정할 때의 버전이 다르면 예외(Exception)를 발생시키고 애플리케이션 단에서 재시도하게 만드는 방식입니다. 읽기가 많은 서비스에서 성능상 유리합니다.
#동시성제어 #비관적락 #낙관적락
